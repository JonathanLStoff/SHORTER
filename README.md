### Components I used (hoverboard drive + flashing rig):
- Hoverboard with 2 motor controller boards, each with its own 4-pin debug/SWD header (GND, SWCLK, SWDIO, 3.3V)
- MCU on each motor controller: GD32E230 (the big chip on both boards), so build the `genericGD32E230C8` env (`TARGET=3`), which the firmware notes as not yet tested
- Arduino Nano clone (ATmega328P, signature 1E 950F, Optiboot at 115200, CH340 USB-serial 1A86:7523, 5V logic, 1 reset button). It is NOT an ESP32. Pins: D2-D10, A0-A7, RX, TX. Not a practical SWD programmer for the GD32 (see below)
- SWD programmer for the GD32E230: ST-Link V2 clone (or a Pico running debugprobe / an ESP32-S3 or C3 with native USB running CMSIS-DAP)
- Firmware: [RoboDurden/Hoverboard-Firmware-Hack-Gen2.x-GD32](https://github.com/RoboDurden/Hoverboard-Firmware-Hack-Gen2.x-GD32) as a git submodule in `hoverboard-firmware-hack-GD32/` (clone with `git clone --recurse-submodules`)
- Flash wiring (programmer -> hoverboard debug header): SWDIO -> SWDIO, SWCLK -> SWCLK, GND -> GND, NRST optional. The programmer must use 3.3V signalling (do not drive the GD32 from a 5V Nano). Power the hoverboard from its own battery and leave the header's 3.3V unconnected unless the programmer needs a voltage reference
- Each board is flashed separately: one at a time with the same wiring, with one firmware build as MASTER and the other as SLAVE (`Inc/configDebug.h`), or both as SINGLE if driven independently

### ESP32-C6 flasher / controller (`swd-flasher/`)
An ESP32-C6 acts as the SWD programmer for the hoverboard's GD32E230 motor controllers (bit-banged SWD, no ST-Link needed). On boot it keeps trying until it works:

| LED (WS2812 on GPIO8) | Meaning |
|---|---|
| blue, blinking | looking for a controller on the debug header |
| yellow | erasing / programming / verifying |
| green | this board is done (flashed and verified, or backup read when no image is embedded) |
| red (2.5 s, then retries) | error |

- **One connector moved from board to board** (`NUM_TARGETS 1`): green when a board is done, blue again when you unplug it, and a newly connected board is handled automatically. Boards are told apart by their unique ID, so plugging a finished board back in does nothing
- **No image embedded = read-only backup mode**: it reads the whole flash, prints it over USB and writes nothing. Only with an image in `firmware/target_a.bin` does it erase and program
- Master and slave can **not** share the same two ESP32 pins: the GD32E230 debug port (DPIDR 0x0bf11477, SW-DP v1) has no multidrop addressing, so both chips would answer at once. Either use the master's port only (it forwards to the slave over the master-slave cable), or give the slave its own pins (SWCLK=GPIO2, SWDIO=GPIO3, `NUM_TARGETS 2`)

#### Hardware and wiring
| ESP32-C6 | Hoverboard 4-pin debug header |
|---|---|
| GPIO1 | SWCLK |
| GPIO0 | SWDIO |
| GND | GND |
| (nothing) | 3.3V: leave unconnected |

- Header pin order, starting from the 3.3V end: **3.3V, SWCLK, SWDIO, GND**. Verified on the master. The first guess (the other way round) got no answer at all
- The hoverboard must be **switched on** (power button pressed, running on its own battery). If it is off, the ESP32's pins back-feed the chip through its protection diodes: the debug port then answers but every memory read is 0 (CPUID=0, flashsize 0). The firmware detects this and reports `NOT a Cortex-M23`
- The ESP32-C6 is powered from USB. The master is the board with the power button (board A); the other is the slave
- Optional second board on its own pins: SWCLK=GPIO2, SWDIO=GPIO3, GND (set `NUM_TARGETS 2` in `src/config.h`)

#### Reproducing it from scratch
1. **Toolchain** (macOS, one time):
   ```sh
   cd swd-flasher
   python3 -m venv .venv
   .venv/bin/pip install platformio   # tested with PlatformIO 6.2.0, ESP-IDF 5.5.0, pyserial 3.5
   ```
2. **Build and flash the ESP32-C6.** Plug it in over USB. If it doesn't show up, try another USB cable (a bad cable was the problem here, twice). Then:
   ```sh
   ls /dev/cu.usbmodem*                                   # e.g. /dev/cu.usbmodem101
   .venv/bin/pio run -t upload --upload-port /dev/cu.usbmodem101
   ```
   With `firmware/` empty this builds the read-only backup mode.
3. **Connect the master**: wire it as in the table, switch the hoverboard on, then plug in or reset the ESP32. Watch the log (`.venv/bin/pio device monitor -p /dev/cu.usbmodem101`). A good connection looks like this:
   ```
   A: controller found (DPIDR=0x0bf11477 uid=4337485409544c573453827e)
   A: CPUID=0x411cd200 (Cortex-M23 as expected) FMC_OBSTAT=0xffffff00 (not protected)
   DUMP BEGIN uid=4337485409544c573453827e flashsize_kb=64
   DUMP END OK crc32=a790a40c glitches=0
   A: done. Unplug and connect the next board whenever you like.
   ```
4. **Capture the stock firmware twice and compare.** The script resets the ESP32, collects the `DUMP` lines and checks them against the CRC32 the ESP32 computed while reading:
   ```sh
   .venv/bin/python scripts/capture_dump.py /dev/cu.usbmodem101 backup/run1.bin
   .venv/bin/python scripts/capture_dump.py /dev/cu.usbmodem101 backup/run2.bin
   cmp backup/run1.bin backup/run2.bin && echo identical
   ```
   Only keep a capture when **both** are identical, show `CPUID=0x411cd200`, `flashsize_kb=64`, `glitches=0` and a full UID. Then keep one copy:
   ```sh
   mv backup/run1.bin backup/master_stock.bin && rm backup/run2.bin
   shasum -a 256 backup/master_stock.bin > backup/master_stock.bin.sha256
   ```
5. **Slave**: move the 3 wires to the slave's header (hoverboard still on). The LED goes blue, then green. Repeat step 4, saving as `backup/slave_stock.bin`. Leave a few seconds between captures.

#### Flashing a board (new firmware, or restoring the stock backup)
Flashing **mass-erases** the chip: have a verified backup first.
1. Put the image to write in `swd-flasher/firmware/target_a.bin`:
   - restore stock: `cp backup/master_stock.bin firmware/target_a.bin` (or `slave_stock.bin` for the slave)
   - new firmware: build it as described in `swd-flasher/firmware/README.md` (master and slave need different builds)
2. `.venv/bin/pio run -t upload --upload-port /dev/cu.usbmodem101`. `scripts/gen_images.py` embeds the `.bin` automatically. The image is sanity-checked first (stack pointer in RAM, reset vector in flash, at most 64 KB), and a bad file is refused.
3. Connect only the board this image is for, with the hoverboard on. The LED goes yellow (erase, program, verify), then green, and the board restarts with the new firmware.
4. **Remove `firmware/target_a.bin` and re-upload before connecting the other board.** With one connector, whatever image is embedded is written to every new board you plug in.

If the chip is read-protected, the flasher removes the protection, which also erases it (`ALLOW_UNLOCK`, at most 3 tries per board).
First power-up with motor-driving firmware: use a current-limited supply (1-2 A) and keep the wheels off the ground. The board layout (`LAYOUT` in `configDebug.h`) is not confirmed yet (2.3.3 ruled out, 2.3.1 or 2.3.2, probably 2.3.2), and a wrong layout can short the battery through the MOSFETs.

#### Problems we hit and how they were fixed
| Symptom | Cause | Fix |
|---|---|---|
| `ACK=111`, SWDIO floating, no answer | SWCLK/SWDIO assumed in the wrong order | Header order is 3.3V, SWCLK, SWDIO, GND; config set to SWCLK=GPIO1, SWDIO=GPIO0 |
| Debug port answers but CPUID=0, flashsize 0, reads all zero | Hoverboard switched off, chip half-powered through the SWD pins | Switch the board on with the power button |
| `ACK=OK` but DPIDR always `0xfc0f801b` (same at every clock speed), next command fails | ESP32 default pin drive (strength 2) rings on the soldered wires, so the GD32 sees extra clock edges | `SWD_DRIVE_STRENGTH 0` (weakest). Measured: strengths 0 and 1 read the correct 0x0bf11477, 2 and 3 return garbage |
| Backups identical every run but every 32nd word 0, CPUID=0, `glitches=492` | The GD32E230 only returns valid data on the **first** RDBUFF read after an AP read, and repeated reads give 0. A majority vote over repeated RDBUFF reads always picked 0 | Read RDBUFF once; verify by reading every block twice and comparing. The simulator in `test/` now models this (`cd test && make test`) |
| LED red forever although the backup worked | Backup mode treated "found but no image" as an error, and waited for a second board that wasn't wired | A finished backup counts as done (green); `NUM_TARGETS 1` |
| ESP32-C6 not showing up on USB | Charge-only cable | Use a data cable |
| ESP32-C6 silent, LED dark, log shows `boot:0x4 (DOWNLOAD...) waiting for download` | The USB port's DTR/RTS lines dropped it into download mode during a reset, and it stayed there through resets | Unplug the USB cable for 5 s. Or just reflash it: `pio run -t upload` works in download mode |
| Uploading through the board's second USB-C port ("UART", shows as "USB Single Serial") fails with `Checksum error` / `message is invalid`, and erased the ESP32's bootloader | Data corrupted through that port's USB-UART chip | **Always flash the ESP32 through the native USB port** ("USB JTAG/serial debug unit", `/dev/cu.usbmodem101`). Logs appear on both ports |
| ESP32 port keeps disappearing every few seconds, LED dark | No bootloader (after the failed upload above), so it keeps restarting | Recovery below |

**Recovering the ESP32-C6 if it won't boot** (its ROM loader can't be erased, so this always works):
1. Plug into the native USB port. If the port keeps disappearing, catch it in download mode by running this repeatedly until it prints `Staying in bootloader` (or hold BOOT, tap RESET, release BOOT):
   `esptool.py --chip esp32c6 --port /dev/cu.usbmodem101 --after no-reset chip-id`
2. Flash everything:
   `esptool.py --chip esp32c6 --port /dev/cu.usbmodem101 --before no-reset write-flash 0x0 .pio/build/esp32-c6/bootloader.bin 0x8000 .pio/build/esp32-c6/partitions.bin 0x10000 .pio/build/esp32-c6/firmware.bin`
3. The flasher boots (`boot:0xc (SPI_FAST_FLASH_BOOT)` in the log) and the LED test runs

Built-in troubleshooting:
- If no controller answers on the configured pins, the ESP32 scans GPIO 0-7, 10, 11 and 18-23 for any SWCLK/SWDIO pair that answers, checks for shorts between pins, and switches to the pair it finds (logged as `scan: ...`)
- `SWD_LINK_DIAG 1` in `src/config.h` prints a raw bit trace of the ID read at several clock speeds and drive strengths on every boot. That is how the ringing problem was found
- Slower clock: raise `SWD_HALF_PERIOD_NS` (default 500 ns, about 1 MHz)

#### Controlling the boards later
The debug ports are the only free connection (no spare holes for UART), so the plan is to control the boards over SWD. Custom firmware will read a command block in RAM (speed, steer, heartbeat) that the ESP32 writes over the debug port, and stop the motors if the heartbeat stops. The master forwards the slave's share over the original master-slave cable. This firmware change is not written yet. The older UART plan (`REMOTE_UARTBUS` on GPIO16/17) in `swd-flasher/firmware/README.md` is replaced by this.
